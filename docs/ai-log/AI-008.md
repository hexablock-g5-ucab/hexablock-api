- **Task** · FR-015 (registration and login with JWT), part 1 of class model v6.3 ([05-api.mmd](../diagrams/05-api.mmd)). Adds `User`, email normalisation, the `UserRepository`, `PasswordHasher` and `TokenService` ports, application errors, and the `RegisterUserUseCase`, `LoginUseCase` and `ReadProfileUseCase` use cases. - **Prompt, paraphrased** · Implement auth part 1 with domain, ports and use cases only. Use no Prisma, bcrypt, JWT library or Nest in `src/domain` or `src/application`. Normalise emails, reject duplicates, never store or return the plain password, and always register a player. Login must give the same error for an unknown email and a wrong password, and must still verify against a fixed dummy hash when the email is unknown. Write unit tests with in-memory fakes, plus an architecture test that rejects framework imports in the inner layers. Do not commit.
- **Output** · Domain (`src/domain/users`), ports with injection tokens (`src/application/ports`), errors (`src/application/errors`), use cases and their unit tests (`src/application/use-cases/auth`), fakes (`test/helpers`) and the layer-boundary test (`test/architecture`).
- **Decisions taken by the assistant, to be confirmed in review**
  - `create` receives `role` so the use case, not the adapter, states that registrations are players. The prompt listed `create({ email, passwordHash, displayName })`.
  - The use case gets the dummy hash by hashing a constant through the port on first use, so it always matches the adapter's format. The first unknown-email login therefore does one extra hash.
  - The existing `LoggingUseCase` imports `@nestjs/common`. The architecture test lists it as a known violation, and fails if that file stops violating. It is to be fixed with the model's `LogPort` in its own PR.
